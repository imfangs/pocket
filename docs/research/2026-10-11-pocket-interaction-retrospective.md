# Pocket 迭代复盘：操作类产品怎样做到顺手

日期：2026-10-11。回顾范围：2026-09-27 创建项目，至 10-11 设置与平台入口精简。用途：供 Pocket 后续迭代，以及控制台、任务执行入口、内容工作台等以操作为主的项目参考。

2026-10-13 补记见第九节：补入全局反馈与桌面兼容两轮的新证据，并把已有原则接入实际开发和 FBT 维护入口；前八节保留原回顾范围。

**核心判断：让用户把注意力用于自己的事情，让系统承担记忆、状态管理和恢复。功能的价值，要放进一次完整使用过程里判断。**

这份文档分两种读法：想了解项目经过，读第一、二、五节；要借鉴到另一个项目，重点读第三节的“顺手”标准、第四节的功能取舍和第七节的验证方法。

一个需要纠正的叙事是“到最近才发现手机接续是核心”。09-27 已经提出手机入口，[09-29 早期复盘](2026-09-29-pocket-build-retrospective.md)明确写下了“手机上找到 Mac 正在做的任务，看懂进展，在需要时补上一句话”。最近的工作是让界面更符合已有定位。**写清定位以后，仍需要持续检验每个入口是否服务它。**

## 二、项目经过中真正改变判断的几件事

| 变化 | 反馈或证据 | 得到的认识 |
| --- | --- | --- |
| 任务架转向手机接续 | 最初需要整理越来越多的会话；随后需要在手机上看进展、发指令，09-29 已记录比远程桌面操作更方便的个人反馈 | 主体验应围绕找会话、读进展、继续操作；整理结构要接受实际使用检验 |
| 入口可达之后，继续补齐操作闭环 | 能看到历史时，原执行实例仍可能未连接；请求已接收时，回复仍可能很晚才显示 | 打开页面、看到历史、操作被接收、看到结果是不同环节，验收要走到用户能继续下一步 |
| 新建从选目录转向先写 Query | 用户很少重新查目录，希望沿用上次选择、标题可空，并保留刚提交的内容 | 默认值、自动拟题和输入优先，比多一个快捷按钮更能减少重复劳动 |
| 整理功能逐步退出主界面 | 分组、安排、备注、两页签、来源设置和重复入口陆续被指出无用 | 初版做过的能力可以退休；低频能力也可以移位，不必拥有常驻区域 |
| 剪贴板读取去掉后又恢复 | 为避免系统 Paste 提示而去掉自动读取，会失去预填；方帅了解代价后明确选择恢复 | 判断便利性要比较完成任务的总负担，不能只看第一步是否干净 |
| UI 从统一样式进一步转向结构精简 | 先统一颜色、排版和按钮，随后继续删除区域、合并状态、调整入口位置 | 视觉规范帮助一致，信息优先级和操作路径仍需要单独设计 |

这些变化来自具体使用反馈，不应被整理成一条“所有项目最后都应该越来越少”的规律。Pocket 是个人手机入口；团队资料管理、多人审批和探索型工具可能有不同取舍。

## 三、“顺手”怎样变成可检查的标准

对操作类产品，可以暂时这样定义：**用户能直接开始预期动作，清楚自己在操作什么和系统做到了哪一步；中断或犯错后，仍能接上已有工作。**

“顺手”包含寻找、判断、输入、等待和恢复的成本。少一次点击可能有帮助，也可能把一个可见按钮藏成了难找的手势。下面的标准需要放在目标设备和真实任务里检查。

| 环节 | 希望观察到的行为 | 最小检查方式 | Pocket 的对应例子 |
| --- | --- | --- | --- |
| 开始 | 已有意图可以直接进入操作；系统知道的内容不反复询问 | 分别从空白和已有素材开始，记录重复选项、搬运内容和被打断的地方 | 先写 Query，复用有效目录，标题留给 Codex；目录失效时才补选 |
| 找到与选择 | 列表提供足以决定下一步的信息，范围与含义清楚 | 放入运行、等待、完成等已知对象，观察误入详情和反复返回的原因 | 运行计数可以直接过滤；归档数量缺少当前决策价值，因而被移除 |
| 执行动作 | 入口靠近目标，当前设备上有用；用户理解会改哪里 | 让人完成一次操作，并说明预期对象和后果；同时检查键盘与触摸 | 信息面板的“在 Mac 打开”只在 Mac 显示；Pocket 置顶与原会话重命名保持不同语义 |
| 等待 | 已提交内容有稳定落点，状态足以决定继续、等待或核对 | 延迟响应，模拟服务端完成但客户端丢失回复，观察是否产生误重试 | 创建卡、待发卡与新草稿分开；已接收、模型完成、结果未知分别表达 |
| 离开与回来 | 已写内容、选中对象和阅读位置在承诺范围内保留 | 写半条消息、选附件、向上阅读，再切任务、开弹窗、收键盘和切后台 | 草稿与附件连续性，键盘收起后的全屏恢复，向上阅读时不抢滚动位置 |
| 犯错与恢复 | 能确认哪些已生效；输入保留，并有与后果相称的下一步 | 制造名称冲突、权限拒绝和网络中断，检查核对、修正和重试 | 未知结果按原编号核对；确认未改名后允许再次保存，不能把不确定当成未执行 |

记录具体片段比给一个“体验 90 分”更有用。例如：用户为什么打开了三个菜单、哪里重新输入了相同内容、何时以为没发成功。需要比较速度时，分开人的操作时间、系统等待时间和结果出现时间，用同一任务前后对照；没有测量就保留为设计判断。

还有两组应分开的观察：首次使用看入口能否找到，熟练使用看是否仍有重复劳动；页面内返回看当前草稿能否接上，系统终止进程后重开看产品实际承诺的持久化范围。不能用其中一项通过代替另一项。

## 四、功能精炼：决定保留什么、放在哪里

每项能力至少需要回答：它服务哪一个实际动作？提供什么独有价值？使用频率和出错后果如何？是否需要用户每次判断？如果移走，剩下的路径是否仍容易找到、可以恢复？

频率和后果要一起看。停止执行可能用得少，但需要时应及时找到；一个常驻计数即使总能显示，也未必帮助决策。

| 处理方式 | 适用判断 | Pocket 的例子 |
| --- | --- | --- |
| 保留在主路径 | 经常使用，或当前状态下必须及时行动 | Query 输入、发送、运行筛选、运行中的停止 |
| 交给可靠默认值 | 通常重复同一选择，系统能检查其有效性，并允许纠正 | 上次目录、可选标题、原会话模型和权限继承 |
| 按需出现 | 有价值，但不应持续占阅读和输入空间 | 点击标题查看会话信息、重命名和归档 |
| 随设备或能力显示 | 在一类设备上有用，在另一类设备上有等效路径或无实际用途 | 手机保留下拉刷新，鼠标桌面保留按钮；Mac 快捷入口按系统显示 |
| 从界面退休 | 实际使用缺少收益，或与其他入口重复 | 自定义分组、安排、备注编辑、重复管理入口及跳转按钮 |
| 保留在实现或维护工具中 | 用户无需经常操作，但恢复和正确性仍依赖它 | 原数据与自动备份、发送账本、兼容性校验、请求去重；发布号门槛的后续修正见第九节 |

**剪贴板是减法的重要反例。** iOS 的 Paste 许可属于系统行为，网页无法用样式把它消掉。当时验证了自动剪贴板请求不再发起，预填也被移除；没有完成 iPhone 系统许可弹层的实机验证。方帅选择恢复，说明“少一个提示”不能单独决定方案优劣。需要更早解释这种取舍，再按真实偏好选择。[过程与恢复决定](../design/2026-10-09-startup-and-query-entry.md)

同样，不能为了简洁抹掉未知结果、执行范围和失败后的处理方式。界面可以减少说明的常驻面积，关键状态必须在需要时准确出现。删除界面时还应说明旧数据怎么处理；Pocket 此轮保留了旧数据和兼容接口，没有把删除入口等同于清空数据。

## 五、UI 的多轮打磨，究竟改了什么

UI 的作用包括信息优先级、操作位置、反馈和连续性。图形与颜色的一致性是其中一层，需要和完整操作一起看。

| 层面 | 前后变化 | 可借鉴的判断与证据 |
| --- | --- | --- |
| 信息层级 | 列表有重复“会话 / 选择”、统计和辅助说明，随后移除；标题与当前状态更突出 | 先判断每块信息是否帮助当前决策。[10-10 对照](../design/2026-10-10-interface-subtraction.md)中首条任务上移 44px；这是版面证据，尚未测得找任务时间的改善幅度 |
| 默认路径 | 新建先强调目录搜索，后来先写 Query，其他设置按需展开 | 在人已有意图时保护表达；隐藏字段失效时仍要能定位并纠正。[新建演进](../design/2026-10-09-startup-and-query-entry.md) |
| 入口位置 | 右上管理与管理页签并存；先合并，后删除两页签，改为点击标题打开信息 | 低频操作靠近对象，主区域持续用于对话；移动入口后检查可发现性、焦点返回和草稿。[最终收敛](../design/2026-10-11-brand-and-interface.md) |
| 状态与动效 | 发出后不易辨认；补上独立提交卡、绿色接收反馈、蓝色队列反馈，并把运行与计时同排 | 颜色和动效表达真实状态；未知、暂停、编辑不应假装正在推进。文字含义和减少动态效果仍保留。[反馈契约](../design/2026-10-09-creation-and-send-feedback.md) |
| 空间与输入 | 输入框长高会挤走最新内容；键盘收起后可能残留旧视口并露出列表 | 看整个输入、收起和返回过程。合成复现验证了位置与草稿恢复，实际输入法回跳仍需真机反馈。[连续性](../design/2026-09-30-steady-interaction.md)、[键盘恢复](../design/2026-10-10-keyboard-recovery.md) |
| 视觉一致性 | 菜单用通用线框口袋，启动图是绿色叠层；随后采用同一矢量主稿生成各处资产 | 一个品牌标志需要覆盖菜单、登录、启动、离线与安装图标，并处理旧缓存；小尺寸清楚不代表用户已经喜欢它。[品牌主稿与检查](../../design/brand/README.md) |
| 设备适配 | 同一按钮出现在所有环境；后来按触摸、宽度和系统能力调整 | 窄窗口不等于手机，iPad 桌面 UA 也不等于 Mac。隐藏入口前验证替代路径，保留键盘、触摸及焦点操作 |

这轮对 Notion、Apple、Linear 的参考主要来自帮助文档及其中的交互机制，没有登录完整体验这些产品。Pocket 借鉴的是内容优先、渐进披露、就近操作和准确反馈；没有证据把某个像素或动画参数说成标杆产品的直接做法。[参照与边界](../design/2026-10-08-notion-inspired-workspace.md)

一次可行的 UI 审视顺序是：先看任务目标和信息是否必要，再看默认路径与入口位置，随后核对反馈、输入和返回，最后统一排版、颜色、尺寸与动效。它是帮助发现遗漏的顺序，不是每个小改动都必须重做的仪式。

## 六、这轮协作值得保留和纠正的地方

真实使用推动了问题的具体化。“键盘已经收起但页面没恢复”“发出去后一小段时间什么也看不到”，都比“再高级一点”更容易形成可复现的目标。早期可用版本因此有价值：它把隐藏的问题带到实际操作里。

格得需要承担的反思也很明确：前期更擅长完善已有组件，对哪些结构根本不应保留判断不足。方帅多次要求整体减法后，仍需逐个指出无用区域。先把新建与刷新按钮做成同一视觉风格，随后才发现手机刷新入口重复，就是一个具体例子。后续应主动沿完整路径审视相邻区域，减少让用户充当逐项检查员的负担。

快速反馈可以保留，交付不必碎成每个按钮各跑一轮完整流程。对已经连续提出、属于同一屏幕或同一路径的调整，可以在当前任务内合并实现、统一检查和发布；紧急故障及影响不同的数据操作另行处理。发布后继续核对实际版本，遇到资源切换沿同一部署恢复，避免重复提交。

底层有些复杂性值得保留。Pocket 要把消息交给同一个原执行实例，保留模型、目录和权限；元数据操作可以使用核验过的官方短生命周期进程。应围绕实际所有权和操作后果建立边界，不能把它简化成“所有动作都要另开进程”或“绝不能使用任何第二进程”。

验收也需要说清对象。9 月 30 日一次真实测试确认发送已接收，却发现回复落盘后网页又晚约 55.8 秒才显示；10 月 11 日改名已持久化，原执行实例的标题仍有刷新延迟。这些结果要求继续查用户可见的最后一段，而不能把 API 成功直接写成整个体验完成。[发送与显示的区别](../design/2026-09-30-send-reliability.md)、[改名验证](../design/2026-10-11-rename-and-management.md)

| 证据 | 能支持的结论 | 还需另外确认 |
| --- | --- | --- |
| 回归测试 | 覆盖到的规则、状态转换和保护边界符合预期 | 功能是否值得存在，用户是否容易理解 |
| 合成浏览器与布局检查 | 指定内容、视口和事件下操作可完成，布局和草稿行为符合预期 | 真机键盘、输入法、主屏幕生命周期及实际手感 |
| 公网或原生受控回读 | 指定请求进入了预期对象，并取得相应结果 | 长期网络可靠性，以及用户是否能及时看到、理解结果 |
| 日常使用反馈 | 对该用户、该场景是否省事，哪里仍有摩擦 | 其他用户的需求、通用安装体验和商业价值 |

截至本次复盘，已经有个人使用反馈和大量工程证据；没有系统量化长期节省了多少时间，也没有验证通用产品需求。历史用例中的已删除功能仍可用于解释原因，不能从旧测试通过推断它们应该重新加入产品。

## 七、下一个类似项目怎样借鉴

先选一个用户会反复完成的任务，例如“找到待处理对象并完成回应”“把现成素材变成一次发布”。把开始、执行、等待、离开再回来的过程走通，再决定是否需要额外的组织结构。

一个小范围的检查就可以开始：

1. 用现有版本完成同一个任务，记下寻找、重复输入、误入、反复核对和恢复失败的位置；保留必要的截图或操作记录。
2. 选择其中一个主要摩擦，说明是删除、默认处理、移动入口还是反馈不准确，并列出改动必须保住的内容与行为。
3. 实现后重走原路径，再加一次慢响应或中断、一次设备差异、一个错误恢复场景。具体场景随风险选择，不要求固定数量。
4. 分别记录行为证据与人的感受。低影响样式调整用相关检查；涉及派发、权限和数据的改动验证实际对象及后果，项目已有必需检查继续执行。
5. 后续实际使用推翻了判断就调整，保留原因。单个项目有效的经验先作为候选方法，经过其他场景重复验证后再考虑提炼为通用工作流。

可直接复制到另一项目的简短记录：

```text
实际场景与设备：
用户要完成的目标、可识别的完成结果：
当前最费力或最不确定的一段：
本次选择及理由（保留 / 默认处理 / 按需出现 / 移位 / 删除）：
必须保住的内容、控制权和恢复路径：
前后观察、证据类型、尚未验证之处：
```

记录够解释本次取舍即可，不必把它扩成另一套需要维护的管理系统。

## 八、适用边界与后续参考

这些经验更适合用户已有明确意图、需要频繁行动并处理结果的产品。迁移时要重新看人的目标和后果：探索型工具可能需要更多可见选项；多人系统需要角色、归属和协作记录；涉及支付、权限或不可逆后果时，确认和审计可能就是必要能力。默认复用、渐进披露、少提示或异步执行，都需要具体理由。

Pocket 后续更值得围绕输入、发送、返回、恢复这一圈取得真实反馈，并继续核对宿主升级兼容性。新的入口应能说明它帮助完成的实际动作，以及为什么要放在这里；暂时说不清，可以先保留为假设。
