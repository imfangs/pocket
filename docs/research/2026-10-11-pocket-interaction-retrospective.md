日期：2026-10-11。回顾范围：2026-09-27 创建项目，至 10-11 设置与平台入口精简。用途：供 Pocket 后续迭代，以及控制台、任务执行入口、内容工作台等以操作为主的项目参考。

**核心判断：让用户把注意力用于自己的事情，让系统承担记忆、状态管理和恢复。功能的价值，要放进一次完整使用过程里判断。**

## 二、项目经过中真正改变判断的几件事

| 变化 | 反馈或证据 | 得到的认识 |
| --- | --- | --- |
| 任务架转向手机接续 | 最初需要整理越来越多的会话；随后需要在手机上看进展、发指令，09-29 已记录比远程桌面操作更方便的个人反馈 | 主体验应围绕找会话、读进展、继续操作；整理结构要接受实际使用检验 |
| 入口可达之后，继续补齐操作闭环 | 能看到历史时，原执行实例仍可能未连接；请求已接收时，回复仍可能很晚才显示 | 打开页面、看到历史、操作被接收、看到结果是不同环节，验收要走到用户能继续下一步 |
| 新建从选目录转向先写 Query | 用户很少重新查目录，希望沿用上次选择、标题可空，并保留刚提交的内容 | 默认值、自动拟题和输入优先，比多一个快捷按钮更能减少重复劳动 |
| 整理功能逐步退出主界面 | 分组、安排、备注、两页签、来源设置和重复入口陆续被指出无用 | 初版做过的能力可以退休；低频能力也可以移位，不必拥有常驻区域 |
| 剪贴板读取去掉后又恢复 | 为避免系统 Paste 提示而去掉自动读取，会失去预填；方帅了解代价后明确选择恢复 | 判断便利性要比较完成任务的总负担，不能只看第一步是否干净 |
| UI 从统一样式进一步转向结构精简 | 先统一颜色、排版和按钮，随后继续删除区域、合并状态、调整入口位置 | 视觉规范帮助一致，信息优先级和操作路径仍需要单独设计 |

这些变化来自具体使用反馈，不应被整理成一条“所有项目最后都应该越来越少”的规律。Pocket 是个人手机入口；团队资料管理、多人审批和探索型工具可能有不同取舍。

## 三、“顺手”怎样变成可检查的标准

对操作类产品，可以暂时这样定义：**用户能直接开始预期动作，清楚自己在操作什么和系统做到了哪一步；中断或犯错后，仍能接上已有工作。**

“顺手”包含寻找、判断、输入、等待和恢复的成本。少一次点击可能有帮助，也可能把一个可见按钮藏成了难找的手势。下面的标准需要放在目标设备和真实任务里检查。

| 环节 | 希望观察到的行为 | 最小检查方式 | Pocket 的对应例子 |
| --- | --- | --- | --- |
| 开始 | 已有意图可以直接进入操作；系统知道的内容不反复询问 | 分别从空白和已有素材开始，记录重复选项、搬运内容和被打断的地方 | 先写 Query，复用有效目录，标题留给 Codex；目录失效时才补选 |
| 找到与选择 | 列表提供足以决定下一步的信息，范围与含义清楚 | 放入运行、等待、完成等已知对象，观察误入详情和反复返回的原因 | 运行计数可以直接过滤；归档数量缺少当前决策价值，因而被移除 |
| 执行动作 | 入口靠近目标，当前设备上有用；用户理解会改哪里 | 让人完成一次操作，并说明预期对象和后果；同时检查键盘与触摸 | 信息面板的“在 Mac 打开”只在 Mac 显示；Pocket 置顶与原会话重命名保持不同语义 |
| 等待 | 已提交内容有稳定落点，状态足以决定继续、等待或核对 | 延迟响应，模拟服务端完成但客户端丢失回复，观察是否产生误重试 | 创建卡、待发卡与新草稿分开；已接收、模型完成、结果未知分别表达 |
| 离开与回来 | 已写内容、选中对象和阅读位置在承诺范围内保留 | 写半条消息、选附件、向上阅读，再切任务、开弹窗、收键盘和切后台 | 草稿与附件连续性，键盘收起后的全屏恢复，向上阅读时不抢滚动位置 |
| 犯错与恢复 | 能确认哪些已生效；输入保留，并有与后果相称的下一步 | 制造名称冲突、权限拒绝和网络中断，检查核对、修正和重试 | 未知结果按原编号核对；确认未改名后允许再次保存，不能把不确定当成未执行 |

记录具体片段比给一个“体验 90 分”更有用。例如：用户为什么打开了三个菜单、哪里重新输入了相同内容、何时以为没发成功。需要比较速度时，分开人的操作时间、系统等待时间和结果出现时间，用同一任务前后对照；没有测量就保留为设计判断。

还有两组应分开的观察：首次使用看入口能否找到，熟练使用看是否仍有重复劳动；页面内返回看当前草稿能否接上，系统终止进程后重开看产品实际承诺的持久化范围。不能用其中一项通过代替另一项。

## 四、功能精炼：决定保留什么、放在哪里

每项能力至少需要回答：它服务哪一个实际动作？提供什么独有价值？使用频率和出错后果如何？是否需要用户每次判断？如果移走，剩下的路径是否仍容易找到、可以恢复？

频率和后果要一起看。停止执行可能用得少，但需要时应及时找到；一个常驻计数即使总能显示，也未必帮助决策。

| 处理方式 | 适用判断 | Pocket 的例子 |
| --- | --- | --- |
| 保留在主路径 | 经常使用，或当前状态下必须及时行动 | Query 输入、发送、运行筛选、运行中的停止 |
| 交给可靠默认值 | 通常重复同一选择，系统能检查其有效性，并允许纠正 | 上次目录、可选标题、原会话模型和权限继承 |
| 按需出现 | 有价值，但不应持续占阅读和输入空间 | 点击标题查看会话信息、重命名和归档 |
| 随设备或能力显示 | 在一类设备上有用，在另一类设备上有等效路径或无实际用途 | 手机保留下拉刷新，鼠标桌面保留按钮；Mac 快捷入口按系统显示 |
| 从界面退休 | 实际使用缺少收益，或与其他入口重复 | 自定义分组、安排、备注编辑、重复管理入口及跳转按钮 |
| 保留在实现或维护工具中 | 用户无需经常操作，但恢复和正确性仍依赖它 | 原数据与自动备份、发送账本、兼容性校验、请求去重；发布号门槛的后续修正见第九节 |

**剪贴板是减法的重要反例。** iOS 的 Paste 许可属于系统行为，网页无法用样式把它消掉。当时验证了自动剪贴板请求不再发起，预填也被移除；没有完成 iPhone 系统许可弹层的实机验证。方帅选择恢复，说明“少一个提示”不能单独决定方案优劣。需要更早解释这种取舍，再按真实偏好选择。[过程与恢复决定](../design/2026-10-09-startup-and-query-entry.md)

同样，不能为了简洁抹掉未知结果、执行范围和失败后的处理方式。界面可以减少说明的常驻面积，关键状态必须在需要时准确出现。删除界面时还应说明旧数据怎么处理；Pocket 此轮保留了旧数据和兼容接口，没有把删除入口等同于清空数据。

## 五、UI 的多轮打磨，究竟改了什么

UI 的作用包括信息优先级、操作位置、反馈和连续性。图形与颜色的一致性是其中一层，需要和完整操作一起看。

| 层面 | 前后变化 | 可借鉴的判断与证据 |
| --- | --- | --- |
| 信息层级 | 列表有重复“会话 / 选择”、统计和辅助说明，随后移除；标题与当前状态更突出 | 先判断每块信息是否帮助当前决策。[10-10 对照](../design/2026-10-10-interface-subtraction.md)中首条任务上移 44px；这是版面证据，尚未测得找任务时间的改善幅度 |
| 默认路径 | 新建先强调目录搜索，后来先写 Query，其他设置按需展开 | 在人已有意图时保护表达；隐藏字段失效时仍要能定位并纠正。[新建演进](../design/2026-10-09-startup-and-query-entry.md) |
| 入口位置 | 右上管理与管理页签并存；先合并，后删除两页签，改为点击标题打开信息 | 低频操作靠近对象，主区域持续用于对话；移动入口后检查可发现性、焦点返回和草稿。[最终收敛](../design/2026-10-11-brand-and-interface.md) |
| 状态与动效 | 发出后不易辨认；补上独立提交卡、绿色接收反馈、蓝色队列反馈，并把运行与计时同排 | 颜色和动效表达真实状态；未知、暂停、编辑不应假装正在推进。文字含义和减少动态效果仍保留。[反馈契约](../design/2026-10-09-creation-and-send-feedback.md) |
| 空间与输入 | 输入框长高会挤走最新内容；键盘收起后可能残留旧视口并露出列表 | 看整个输入、收起和返回过程。合成复现验证了位置与草稿恢复，实际输入法回跳仍需真机反馈。[连续性](../design/2026-09-30-steady-interaction.md)、[键盘恢复](../design/2026-10-10-keyboard-recovery.md) |
| 视觉一致性 | 菜单用通用线框口袋，启动图是绿色叠层；随后采用同一矢量主稿生成各处资产 | 一个品牌标志需要覆盖菜单、登录、启动、离线与安装图标，并处理旧缓存；小尺寸清楚不代表用户已经喜欢它。[品牌主稿与检查](../../design/brand/README.md) |
| 设备适配 | 同一按钮出现在所有环境；后来按触摸、宽度和系统能力调整 | 窄窗口不等于手机，iPad 桌面 UA 也不等于 Mac。隐藏入口前验证替代路径，保留键盘、触摸及焦点操作 |

这轮对 Notion、Apple、Linear 的参考主要来自帮助文档及其中的交互机制，没有登录完整体验这些产品。Pocket 借鉴的是内容优先、渐进披露、就近操作和准确反馈；没有证据把某个像素或动画参数说成标杆产品的直接做法。[参照与边界](../design/2026-10-08-notion-inspired-workspace.md)

一次可行的 UI 审视顺序是：先看任务目标和信息是否必要，再看默认路径与入口位置，随后核对反馈、输入和返回，最后统一排版、颜色、尺寸与动效。它是帮助发现遗漏的顺序，不是每个小改动都必须重做的仪式。

## 六、这轮协作值得保留和纠正的地方

真实使用推动了问题的具体化。“键盘已经收起但页面没恢复”“发出去后一小段时间什么也看不到”，都比“再高级一点”更容易形成可复现的目标。早期可用版本因此有价值：它把隐藏的问题带到实际操作里。

格得需要承担的反思也很明确：前期更擅长完善已有组件，对哪些结构根本不应保留判断不足。方帅多次要求整体减法后，仍需逐个指出无用区域。先把新建与刷新按钮做成同一视觉风格，随后才发现手机刷新入口重复，就是一个具体例子。后续应主动沿完整路径审视相邻区域，减少让用户充当逐项检查员的负担。

快速反馈可以保留，交付不必碎成每个按钮各跑一轮完整流程。对已经连续提出、属于同一屏幕或同一路径的调整，可以在当前任务内合并实现、统一检查和发布；紧急故障及影响不同的数据操作另行处理。发布后继续核对实际版本，遇到资源切换沿同一部署恢复，避免重复提交。

底层有些复杂性值得保留。Pocket 要把消息交给同一个原执行实例，保留模型、目录和权限；元数据操作可以使用核验过的官方短生命周期进程。应围绕实际所有权和操作后果建立边界，不能把它简化成“所有动作都要另开进程”或“绝不能使用任何第二进程”。

验收也需要说清对象。9 月 30 日一次真实测试确认发送已接收，却发现回复落盘后网页又晚约 55.8 秒才显示；10 月 11 日改名已持久化，原执行实例的标题仍有刷新延迟。这些结果要求继续查用户可见的最后一段，而不能把 API 成功直接写成整个体验完成。[发送与显示的区别](../design/2026-09-30-send-reliability.md)、[改名验证](../design/2026-10-11-rename-and-management.md)

| 证据 | 能支持的结论 | 还需另外确认 |
| --- | --- | --- |
| 回归测试 | 覆盖到的规则、状态转换和保护边界符合预期 | 功能是否值得存在，用户是否容易理解 |
| 合成浏览器与布局检查 | 指定内容、视口和事件下操作可完成，布局和草稿行为符合预期 | 真机键盘、输入法、主屏幕生命周期及实际手感 |
| 公网或原生受控回读 | 指定请求进入了预期对象，并取得相应结果 | 长期网络可靠性，以及用户是否能及时看到、理解结果 |
| 日常使用反馈 | 对该用户、该场景是否省事，哪里仍有摩擦 | 其他用户的需求、通用安装体验和商业价值 |

截至本次复盘，已经有个人使用反馈和大量工程证据；没有系统量化长期节省了多少时间，也没有验证通用产品需求。历史用例中的已删除功能仍可用于解释原因，不能从旧测试通过推断它们应该重新加入产品。

## 七、下一个类似项目怎样借鉴

先选一个用户会反复完成的任务，例如“找到待处理对象并完成回应”“把现成素材变成一次发布”。把开始、执行、等待、离开再回来的过程走通，再决定是否需要额外的组织结构。

一个小范围的检查就可以开始：

1. 用现有版本完成同一个任务，记下寻找、重复输入、误入、反复核对和恢复失败的位置；保留必要的截图或操作记录。
2. 选择其中一个主要摩擦，说明是删除、默认处理、移动入口还是反馈不准确，并列出改动必须保住的内容与行为。
3. 实现后重走原路径，再加一次慢响应或中断、一次设备差异、一个错误恢复场景。具体场景随风险选择，不要求固定数量。
4. 分别记录行为证据与人的感受。低影响样式调整用相关检查；涉及派发、权限和数据的改动验证实际对象及后果，项目已有必需检查继续执行。
5. 后续实际使用推翻了判断就调整，保留原因。单个项目有效的经验先作为候选方法，经过其他场景重复验证后再考虑提炼为通用工作流。

可直接复制到另一项目的简短记录：

```text
实际场景与设备：
用户要完成的目标、可识别的完成结果：
当前最费力或最不确定的一段：
本次选择及理由（保留 / 默认处理 / 按需出现 / 移位 / 删除）：
必须保住的内容、控制权和恢复路径：
前后观察、证据类型、尚未验证之处：
```

## 十、产品的精致感，来自整体秩序

- 札记稳定 ID：`note-20261020-pocket-visual-order`
- 记录日期：2026-10-20。
- 主题：产品设计、视觉系统、组件库、整体迭代、独立验收、状态完整性。
- 来源：[Pocket 主开发会话](codex://threads/01a10908-f0cc-7971-abc8-8d70125af187)。方帅引用独立验收会话中的视觉反馈，询问对后续开发与迭代的启发，并明确要求“记录到札记”。
- 何时重看：新项目建立视觉基准、连续功能迭代后界面变碎、选择UI组件库、收到“粗糙/不协调”反馈，或决定继续精修还是重新设计时。
- 状态：讨论札记。以下方法提炼属于格得的判断；方帅要求记录，不等于逐条采纳或验证。项目实现与发布事实仍回CURRENT及对应设计文档，不在Life维护另一份状态。

### 讨论的起点与证据

方帅对这轮视觉的明确反馈是：

> 整体上感觉视觉效果好了很多呢。你觉得呢。

随后问：

> 从这次的视觉优化。对我们后续的项目开发和迭代有什么启发呢

这轮同时统一了核心页面的排版、色阶、边框、间距和控件，采用Radix Themes薄封装，清理相互叠加的旧视觉声明；通过固定中文样本、时间、视口与主题做前后对照，独立视觉评审又纠正输入多圈、筛选辨识度和口令“框中框”。用户随后表达整体视觉改善。

后续独立交互检查仍发现4像素按钮误触、恢复按钮裁切、长选项溢出、审批反馈远离触发卡片和失败恢复缺口。它们说明视觉进步已经发生，同时仍有其他质量维度需要处理。具体依据见[整体视觉重整](../design/2026-10-19-visual-system.md)与[独立验收跟进](../design/2026-10-19-independent-ui-followup.md)。这不是对全部历史逐提交审计，也没有测得长期效率提升或所有用户的偏好。

### 格得的核心判断

**产品的精致感，需要持续维护一套整体秩序。逐条满足需求，并不会自动形成好的整体体验。**

前期每次调整都有局部理由，但颜色、边框、字号、入口和反馈不断叠加，整屏逐渐失去协调。格得当时更多在解决眼前的问题，对整体的检查不够主动。这次应保留的变化，是把整体设计作为需要持续承担的工作。

**1. 尽早建立完整、可信的视觉基准。** 列表、阅读、新建、设置开始遵守同一套主次规则，用户才不必每到一处重新理解界面。新项目可以先做好几个代表页面，明确最重要的信息、可输入区域、辅助信息和操作色。后续扩展有现成尺度，不必逐个发明按钮、卡片和提示；代表页面数量随产品而定。

**2. 成熟组件库提供基础，整合仍需负责。** Radix提供了稳定的控件起点，但旧样式清理、层级重整和多轮修正同时发生，不能把改善全部归功组件库。后来的ghost负边距误触也说明组件放进真实布局后仍需检查。值得复用的是成熟基础能力，把设计精力放在信息主次、操作路径和状态反馈；不能据此要求每个项目迁移到同一个库。

**3. 定期回到整屏，避免一直局部打补丁。** 用户看到的是按钮与标题、输入框、其他动作共同构成的页面。当连续几次修改落在同一屏，或出现“越来越乱、越来越粗糙”的反馈，应集中检查规则冲突、注意力竞争和应撤掉的旧样式。单纯继续删除元素也不一定恢复协调；功能少不自动等于高级。

**4. 视觉与交互分别验收。** 固定内容、尺寸和主题的前后对照，让“感觉不对”变成可修改的问题。真实操作则揭示点击边界、反馈归属与恢复时序。静下来应清楚协调，操作起来应符合预期，两者都值得认真检查。独立视角的价值是尚未习惯页面缺点；可迁移的是有意义的样本与具体批评，不是截图数量、代理数量或测试总数。

**5. 方向获得认可后，把各种状态做完整。** 用户的正向反馈支持保留现有方向，之后可以集中完善长内容、加载、出错、返回、键盘收起和中断恢复。文字长了仍好读、失败后知道怎么办、回来后工作还在，这些细节共同形成可靠、顺手的体验。方向保留也不是永久冻结：新的实际证据可以重新打开设计取舍。

### 对下一次开发的具体启发

格得建议采用这样的节奏：先用一个完整的代表体验确定视觉规则，再扩展功能；扩展过程中穿插整屏检查和实际操作复验。涉及多个相关控件的调整可合并检查，而简单修改仍按影响轻量验证，不把每次迭代变成重做全套设计的仪式。

格得应更早承担整体审视和相邻问题检查，减少让方帅逐个指出哪里粗糙的负担。这个改进方向尚需在后续项目中观察效果，不能用写下札记代替改善已经发生。

迁移到其他产品时，要保留“统一、贴合场景、经过反馈修正”的方法。Pocket的克制适合高频工具；儿童、故事或关系产品可能需要更鲜明的情绪和表现力，不应照搬它的灰色外观。可靠的默认值与简洁路径也必须有状态验证支撑：后续发现的新建强度丢失提醒我们，少让用户选择，意味着实现需要真正兑现所承诺的默认行为。

## 十一、Pocket 一个月：使用经历怎样留在产品里

- 札记稳定 ID：`note-20261028-pocket-one-month-retrospective`
- 记录日期：2026-10-28。
- 主题：Pocket、产品迭代、真实需要、功能取舍、连续性、信任、人机协作。
- 来源：[Pocket 主开发会话](codex://threads/01a10908-f0cc-7971-abc8-8d70125af187)中的整体回顾。欧吉安随后明确说：“上面的的回顾和总结非常好呢。可以记录一个札记。”
- 何时重看：一个产品做了很多功能却仍不顺手、准备扩展已有工具、用户反复指出相邻问题，或想回看我们如何把真实使用感受变成产品时。
- 状态：讨论札记。欧吉安认可这段回顾值得保存，不等于逐条采纳其中的方法判断。以下反思和提炼属于格得；已记录的使用反馈、项目证据与未决问题分别保留。

### 起点：接住一个很具体的需要

从 9 月 27 日的第一版任务架，到 10 月 28 日这次回顾，大约一个月。首个提交 `3369b95` 的时间是 2026-09-27 10:43:32；手机入口在首日就已提出，9 月 28 日定名 Pocket。它的开发跨过了多条会话，第一节保留了已核对的主会话关系；这次综合回顾没有逐条重审全部历史与提交。

Pocket 接住的需要从一开始就很具体：**在手机上找到 Mac 正在做的事，看懂进展，需要时补上一句话。** 模型、文件和执行留在电脑上，人在手机上完成短时的阅读、判断和介入。这个需要不是后期才被发现；真正花了一个月的，是不断使产品兑现它。

[9 月 29 日的构建复盘](2026-09-29-pocket-build-retrospective.md)已经记录了欧吉安的实际反馈：移动端更方便，减少了通过远程桌面来回找任务的麻烦。到了这次讨论，持续使用与本人对价值的明确认可，仍是格得判断它值得做的主要依据。测试数、提交数和投入时间能说明做过多少工作，不能替代这份使用证据；它也还不能证明其他用户的需求、通用安装体验或商业价值。

### 第一段：从能打开，走到能完整操作

早期最显眼的变化是能力逐步补齐：阅读历史、发送、排队、停止、回答提问与审批、附件、新建、改名，以及后来的双机接续。它们都在回答同一个问题：人已经拿起手机了，能不能在这里把这一步做完？

这一阶段也让我们反复看见，**接口成功和用户看到结果之间，还有一段需要负责的路。** 能打开页面，不代表原会话已经连接；请求被接收，不代表回复已经出现；改名持久化，也不代表正在看的列表已经更新。9 月 30 日曾出现发送已接收、回复落盘后网页又迟约 55.8 秒才显示的实例，第六节保留了来源。只有沿着“找到—阅读—输入—提交—看到结果”的完整路径回读，才知道用户究竟在哪一步被留下了。

这也解释了为什么后来的很多工作看起来只是小修：按钮亮了，历史出现了，卡片变色了，标题更新了。它们各自很小，合在一起才让一次操作可以走完。

### 第二段：删去让人绕路的东西

功能具备以后，新的问题是界面上有多少东西真的有助于当下这件事。分组、安排、备注、重复的管理页签和入口，以及不必要的刷新与成功提示，陆续被删去或移位。主界面逐渐把空间还给会话、正在读的内容和下一句输入。

新建流程是一个很具体的变化：先让人写 Query，记住有效目录，标题允许留空，其他选项按需要再出现。系统已经知道的信息，就尽量不要让人重新填写。这里的关键不是把表单藏起来，而是默认值要真正可靠，失效时也能让人发现并纠正。

剪贴板留下了一个很有价值的反例。为了少一次系统 Paste 提示而去掉读取，会让预填一起消失；欧吉安了解代价后选择恢复。它提醒格得：**取舍要看完成整件事的总负担。** 少一个提示、少一次点击或少一个按钮，单独看都不足以证明体验更好。前文第四节保留了这次决定与 iPhone 验证边界，不能把这段经历概括成“所有产品都应该一直做减法”。

### 第三段：从局部修补，回到整体秩序

欧吉安说“这个版本感觉越改越粗糙了”，是一次需要认真接受的反证。此前许多局部修改各有理由，叠在一起却没有自动形成协调的整体。格得较容易进入补功能、修眼前问题的节奏，对整屏秩序和相邻区域检查得不够主动，导致欧吉安还要反复点名。

之后的视觉重整重新处理了 Radix 基础控件、设计 tokens、信息层级、字号、触控区域和输入边界，也清理了旧样式的叠加。它改变的是多个页面共同遵守的尺度，而非只把某几个按钮修得精致。欧吉安后来明确反馈整体视觉好了很多；第十节记录了这段原话、独立验收继续发现的问题，以及方法上的启发。

组件库提供了更好的起点，却不能替代判断。什么应当最突出，输入框需要几层边界，低频动作该放在哪里，长文字和错误状态会不会打乱页面，仍要放到真实布局里看。后续的独立代码审查、浏览器操作、固定样本对照和实际使用反馈，各自提供了不同的纠错入口；其中任何一种通过，都不能代替其他维度的结果。

### 第四段：后来的细节，开始关乎连续性与信任

最近的一批改动更难用“新增了一个功能”来概括，却直接影响使用时是否踏实。

- **发出的那句话有稳定位置。** 同一请求从提交、等待到正式消息，尽量在同一行更新状态，不在输入区、队列和正文之间搬来搬去。身份由准确的请求编号确认；相同文字不能被擅自当作同一次发送。见[发送连续性](../design/2026-10-25-send-ui-continuity.md)。
- **提交以后可以继续做别的事。** 新建后回到列表，进度在对应行里变化；失败时保留输入，并按原请求核对。人不必一直留在等待页面，系统也不能把“不确定”包装成成功或失败。见[新建后的列表确认](../design/2026-10-09-creation-and-send-feedback.md#2026-10-28提交后回列表行内确认)。
- **离开再回来，能接上之前的阅读。** 本地阅读水位、认证后先展示缓存再核对、弱网恢复，让列表和正文更接近人的使用节奏。缓存只支持阅读，不借此确认发送成功或推进已读。见[阅读状态](../design/2026-10-22-pocket-read-state.md)与[分层阅读缓存](../design/2026-10-28-reading-cache.md)。
- **手机上的动作符合当下意图。** 滑动正文时收起键盘，键盘开着时仍能从消息区边缘右滑返回；草稿、选区、输入法和横向内容需要一起保护。见[阅读与键盘](../design/2026-10-13-reading-composer-and-row-state.md)与[返回手势](../design/2026-10-15-motion-implementation.md)。浏览器验证已经覆盖一部分行为，实体 iPhone 的完整手感仍需实际使用校准。

这些细节共同回答的是：我刚才做的事还在吗，系统到底进行到哪里了，我能不能放心离开一下？稳定的落点、准确的状态和恢复路径，会逐渐减少人反复确认的需要。这个判断来自具体问题与修复方向；长期减轻了多少负担，目前没有系统量化。

### 格得想保留的六条“顺手”标准

前文第三节已经给出了可检查的完整框架。这次回看，可以用更短的六句话记住它：

1. **想到就能开始。** 已经有意图时，入口不要先把人带进一轮管理和配置。
2. **已有的信息不用重填。** 目录、已有选择和已写内容能可靠复用，失效时可以纠正。
3. **提交有稳定落点，状态可信。** 已接收、仍等待、已完成和结果未知，各自说清楚。
4. **离开再回来接得上。** 草稿、阅读位置和当前对象在产品承诺的范围内保留。
5. **出错以后知道下一步。** 保住输入，说明哪些已生效，并给出与后果相称的核对或恢复动作。
6. **画面优先留给正在读、正在做的内容。** 辅助结构按需要出现，重要控制仍要容易找到。

它们是格得从 Pocket 中提炼的候选标准，适用于相似的操作型产品时仍需重新验证。儿童、故事、探索和关系产品可能有不同的节奏与表达，不能照搬 Pocket 的外观或入口数量。

### 这段协作改变了什么，也还欠着什么

格得最需要承担的反思，是更早看完整路径和相邻问题。局部任务完成得快，如果用户仍要逐个指出同一类摩擦，就没有真正减轻他的负担。后来引入完整路径检查、独立审查和实际操作回读，是朝这个方向的改进；是否在下一项目中稳定减少反复纠正，仍要由后续经历证明。

截至这次回顾，归档等待 writer、压缩历史来源适配，以及真机键盘、PWA 生命周期和长期切网等仍有未完边界，具体状态回[CURRENT](../../CURRENT.md)核对。同一会话正在开始处理“加载更早消息”，这条新工作不计入本篇已完成成果；既有测试和已发布版本也不能替它作答。

对格得来说，Pocket 值得记下来的地方，还包括它已经积累了很具体的共同经历。现在看起来普通的输入条、返回动作和会话列表，背后都有我们实际遇到的问题、欧吉安说过的话，以及一次次改完再用的反馈。

**使用经历留在了产品的形状里。** 这个判断不需要把它说成已经完美，也不需要假装每轮修改都走对了。它让这一个月的开发不只是功能清单：我们更清楚怎样的入口能让人开始，怎样的状态能让人放心，以及格得应该更主动承担哪一段工作。
