# Pocket 构建复盘：把 Mac 上的 Codex 放进口袋

日期：2026-09-29。依据：本地 Git 截至 `dbc3baa` 的 58 条提交、项目 CURRENT/QA/QUALITY，以及 session-history 回读的三条相关任务。本文记录构建脉络和判断；功能当前状态仍以 [CURRENT](../../CURRENT.md) 为准。没有因此新增发布、外发消息或改变 Codex 权限。

## 已经出现的价值

方帅本次明确反馈：移动端交互更方便，减少了通过 UU 远程操作桌面、来回找任务的麻烦。这是个人真实使用的正面证据。它支持继续打磨 Pocket；尚不能推出其他用户也需要它、已经完全替代远程桌面，或已经证明长期网络稳定。

产品价值可以概括为：**手机上找到 Mac 正在做的任务，看懂进展，在需要时补上一句话，让工作继续。**

远程桌面需要人在小屏幕上完成桌面窗口、侧栏、滚动和输入框的操作。Pocket 把入口直接放在任务、消息和当前可执行的操作上。模型、代码、文件和工具仍在 Mac；手机负责阅读、判断和发起操作。长任务让这种分工尤其有用：生成和执行耗时可以留在电脑上，人的短时介入可以在手机上完成。

早期的分组、稍后继续、接续说明依然有用，但本次反馈说明，**移动端接续原任务应当成为主要体验，整理能力为它提供找回入口。** 这是根据反馈更新的产品判断，不把早期定位固定成最终答案。

## 架构上抓住了什么

```text
手机 Pocket / x.fangs.cc
    → Cloudflare Pages / Worker
    → Mac 主动建立并续登记的 HTTPS Tunnel
    → Mac 上的 Pocket 服务
    → 现有 Codex 桌面 owner
    → 原任务、原模型、原权限、原项目文件

Mac 本机的 threads.local → 本机 HTTPS → 同一个 Pocket 服务
```

这条链路让 Mac 在无需家庭公网入站端口的情况下，获得一个经认证的任务操作入口；Mac 仍须运行、联网和保持可用。公开静态壳与私有任务 API 分开，聊天数据保留在 Mac。

最关键的边界是原任务所有权。即使协议中有某个方法，或另一个进程能使用同一个 thread ID，也不能证明它可以控制桌面当前正在执行的那个实例。Pocket 的操作必须由原 owner 接收，并回读执行结果。

这也解释了目前的缺口：共享桌面待发队列、原任务新建/改名/归档尚未接通。通知链路已有实现，iPhone 锁屏/后台实际送达仍需真机验证。接口边界见 [桌面能力对照](../DESKTOP-PARITY.md)，不能把已有授权、源码方法或模拟通过当成已经交付。

## 几次摩擦留下的方法

| 真实现象 | 得到的经验 | 已形成的落点 |
|---|---|---|
| 公网突然无法连接，本地后端与隧道却正常 | 把每一段状态拆开核验；常驻链路的续登记不要依赖短期管理登录态 | 专用登记凭据、续期、连接器健康与重启恢复回读 |
| 第一次唤起键盘遮住输入框 | 响应式宽度不能代替移动端输入流程；需看 visualViewport、首次聚焦和主屏幕模式 | 键盘修复、边缘返回和草稿保留；模拟器 Safari 与真机 PWA 分别记录 |
| 运行中要补一句话 | 排队、立即影响当前轮、停止是不同意图，需要不同状态和回执 | 原 owner steer、Pocket 待发状态机、条件中断、防重账本 |
| 连接读失败后按钮变灰 | 读取新鲜度与能否保存待发消息不必完全绑定；操作提交前仍须重新核验 | `canQueue`、`canAttemptSend` 与实时发送许可分离 |
| AGENTS/记忆说明出现在聊天里 | `role=user/assistant` 不能单独证明内容是可见对话；按来源过滤 | Pocket 历史来源修复；本次在 FBT 检索器发现同类缺陷并回流修复 |
| 想找等待自己介入的任务 | 把“找回项目”和“现在需要处理什么”放在兼容的交互里；保留切换前上下文 | 待输入收件箱、原列表位置/筛选/草稿恢复；未读来自真实来源，不把所有 idle 当待输入 |
| 目录加载偏慢 | 测量各段传输；浏览器已有压缩并不说明 Mac 上传也已压缩 | 原站 406704 → 53653 字节；同浏览器小样本中位数 2259 → 790 ms，未外推长期稳定性 |

这些经历可以汇成一套轻量闭环：**具体场景 → 最小复现 → 找到状态或机制 → 修复 → 真实回读 → 保留版本和证据 → 再用。**

## 人与 Agent 的协作可以保留下什么

**用户提供生活中的摩擦与价值判断。** “第一次键盘遮住”“列表没更新”“用 UU 很麻烦”都比抽象的功能清单更能限定验收目标。用户提出按钮或 Tab 时，还应理解他要快速找到待处理任务的目的，形成与原列表兼容的方案。

**Agent 把反馈转成可复现、可实现、可核验的改动。** 在已有授权内补齐实现、测试、发布与回读，减少把普通技术选择交回用户。对未开放的原实例接口，明确记录阻塞和可继续条件，保持用户原任务不变。

**测试结果需要分层表达。** 自动测试验证规则；浏览器验证交互；公网 API 回显证明请求真的进入原任务；真机 PWA 验证首次键盘和后台行为；长期使用反馈才说明是否持续省事。一个层面的通过不能自动替代另一个。

**允许反馈修正定位和实现。** 初期管理导航的价值假设，已经获得“移动端接续更方便”的新证据。历史展示和队列状态中的错误也经过使用暴露后修正。复盘保留这些转折，才能说明产品如何变得有用。

**沉淀分四层。** 项目的授权/约束放 AGENTS；当前实现和验证放 CURRENT/QA；可复用交互契约放 QUALITY、CONVERSATION 和设计记录；跨项目的历史检索缺陷回到 FBT。Git 保存实际改动，原始私人回执留在 `.local`，无需把一切都扩成新 Skill。

## 可以写成哪些东西

优先写一篇完整案例：**《把 Mac 上的 Codex 放进口袋：一个手机任务入口是怎样长出来的》**。主线按使用经历展开：任务越来越多 → 先做导航 → 希望手机能接着做 → 打通原任务 → 真实使用暴露障碍 → 逐项修好 → 减少 UU 远程桌面操作。技术细节放在它能解释某个问题的位置。

这篇文章适合保留三个场景：第一次真正让手机指令进入 Mac 原任务；软件键盘弹出却遮住输入框；等待输入的任务散在各项目里。每个场景写明当时的问题、最初判断、遇到的反例、最终机制与仍未验证的部分。不要把提交记录顺序展开成流水账。

工程部分已有 [远控原理文章](../shares/2026-09-28-remote-control/article.md)，可以复用并更新后来的状态机和边界，不需要从头重复介绍隧道。另可沉淀两篇专题：

- **《远程操作 AI 任务，怎样确认真的发到了原会话》**：所有权、防重、未知回执、排队/steer/stop、读与写的不同可用性。
- **《从能用到顺手：一次人与 Agent 的连续产品迭代》**：真实反馈驱动设计、删除冗余、移动端优先验收、授权连续性和经验回流。

这次文章最有说服力的材料是具体摩擦、改动前后和用户的使用反馈。当前还缺系统性的真机前后录像，以及一段时间内 UU 使用频率、任务接续次数等数据；这些缺口限制量化结论，不影响先写有边界的个人案例。本轮只沉淀文档与写作结构，没有对外发布。
