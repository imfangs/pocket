# 原会话连接恢复

2026-10-05。方帅反馈多个任务显示“显示已保存的历史。连接 Mac 中的原任务后可发送消息。”，举例“格得 - 修炼”。

## 复现与原因

- 同一目标的落盘历史可读，但原桌面 owner discovery 在 2 秒和 10 秒预算下均超时；当前工作会话约 60 毫秒可读，不能把此问题归为 Mac API 或整个公网链路离线。
- 使用 Pocket 原有的 `codex://threads/<id>` 打开目标后，首轮 10 秒仍超时，第二轮约 115 毫秒返回 `desktop / idle / canSend:true`。这证明该样本需要桌面加载以及等待初始化；没有向目标发送测试消息。
- 原 `/api/open/:id` 只回执已请求打开，不等待原会话可用，也不清除旧历史缓存。显式入队只存正文，随后自动队列仅查找已有 owner，不会启动桌面加载；因此可能长期等待连接恢复。
- Python 将各种连接错误合并为 `desktop_unavailable`，网页无法区分 owner 查找超时、读取快照超时或 App 未运行。

私有现场证据：`.local/qa/connection-2026-10-05/xiulian-before.json` 与 `xiulian-open-readback.json`。这解释了已复现对象，不代表所有连接失败均只有此原因。

## 修复契约

- 用户点击连接时，立即返回操作编号与 `connecting`，后台打开原深链并等待原 owner。整体 45 秒预算，以有界间隔重读；第一次初始化超时可以继续读取，快速返回“加载中”也不会提前耗尽尝试次数。
- 连接成功要求原快照 `source=desktop` 且 `resumeState=resumed`；等待审批的已连接会话仍可能不能发送，两者独立。
- `POST /api/open/:id` 保留原 `handoff_requested` 和 `thread`，增加 `connection`；`GET /api/tasks/:id/connection` 只读状态，历史响应也附带状态。打开请求成功不再被描述为已经接通；已归档任务仍可只读打开，不允许因此恢复发送。
- 用户显式提交后，若尚未连接，先保留待发正文，再尝试一次接入；已在运行、暂停或未知结果仍沿用原队列规则。普通历史刷新和后台队列轮询不打开桌面，不反复抢焦点。
- 对确认尚未派发的连接失败可保存待发并恢复连接；已经派发但结果未知时不自动重放。回读已确认接收的消息不能因迟到的失败被重新入队。
- 连接操作按任务合并；新连接废弃旧缓存，过期读取不得覆盖新连接快照。前端仅轮询同一操作编号，切换任务取消该视图的读取，草稿保留。
- 失败只返回固定原因码，不透出 IPC 原始异常或会话内容；恢复后仍用原 owner，继承原模型与权限。

## 验证与发布

服务端连接恢复和桥接原因字段均先建立失败回归再修复。230 项全量测试及构建通过；独立审阅补齐快速初始化、归档只读打开和旧失败提示三项问题，并独立验证认证、Origin 与 CSRF 拦截。

390×844 内置浏览器验证：连接中保留草稿、慢启动最终可发送、超时显示重试、切换任务后草稿不丢、显式入队只打开一次并产生一条合成回显；无页面错误与横向溢出。证据为 `.local/qa/connection-2026-10-05/browser.json` 和 `ui-fixture-state.json`。

项目既有受控验收对象真实复现 `owner_lookup_timeout`，入队回执约 10 毫秒返回；自动接入后约 22.5 秒读到指定回复与 accepted 回执。原轮次 completed，仅 userMessage/agentMessage，0 工具调用；没有重发。证据为同目录 `live-echo.json`、`live-turn.json`。这不是 iPhone 真机或长期切网验收。

本机服务通过 FBT local 更新，用户分组、注释、既有待发与发送账本在重启前后未改变；来源同步设置按正常流程刷新。公网发布身份以 `CURRENT.md` 最终回读为准。

公网源码 `7233fbe`，Pages 部署 `ff866726-fdaf-4ac5-a712-74b93e766b27`，14 个公开文件哈希匹配、功能检查及 ready=true。独立公网对原“修炼”任务 POST 连接约448毫秒返回 connecting，随后回读 connected、desktop/resumed/idle/canSend=true；没有向此私人任务发送测试正文。内置浏览器启动与 `pocket-build` meta 匹配，未见页面错误。

收尾限制：真实验收对象完成后，恢复原归档被原桌面 App Server 的独占 writer 锁拒绝，独立回读确认仍未归档且内容未改变。已完成不等于 writer 已关闭；本轮保留原记录，未删除锁、重启 Codex 或反复重试。待原实例归档或正式释放后恢复，私有回执 `canary-archive-restored.json`。该边界已回流到 FBT 的归档文档。

## 同轮能力复核

安装版本仍为 `26.903.71938:8576` / CLI `0.153.4`。FBT 于 10-04 已验证官方 CLI 的归档/恢复，以及 `codex exec --json` 创建独立持久任务；见 [codex-threads](../../../../fbt/experimental/codex-threads/README.md)。因此旧文档中笼统的“新建/归档均无接口”已过时。

- 原归档有官方短生命周期 CLI 路线，不用 Pocket 隐藏替代；归档子树、活动任务与待发队列需要在接入时处理。此次还确认已完成但仍由桌面持有 writer 的任务会令独立 CLI 归档失败，必须由原 owner 归档或正式释放 writer 后再处理。持久化回读不等于桌面侧栏即时刷新。
- 新建并开始执行已有 CLI 路线；CLI 本轮执行期间仍由其进程持有，打开页面不等于转交桌面托管。Pocket 的“新建 → 首轮发送 → 停止/审批 → 后续接续”尚未完成集成验证。
- 本轮修复已有会话的接入与发送恢复，不把新建/归档按钮描述为已交付。

## 2026-10-17 首次 owner 查找的立即拒绝

原生router的`no-client-found`在owner发现阶段表示没有匹配客户端，不能直接当作协议不兼容而终止正常打开流程。Pocket现在只在未派发且处于owner阶段时将此精确错误标成`owner_unavailable`；初始化或其他错误仍保持原判定，派发后仍为unknown。恢复仍须核对正确owner、v11快照和resumed状态，不因该错误直接授权发送。多机真实首发、单次导航及原requestId唯一回显证据见[10-17连接补充](2026-10-17-multi-machine.md#真实连接补充首次未找到-owner)。
