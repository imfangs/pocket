# 长会话发送超时与回执

2026-09-30。用户反馈网页连接和发送不稳定，询问是否来自最近改动。

## 证据

- 最近两项产品改动为前台认证检查顺序和本地图片展示；发送协议未在这两次修改。Mac 后端自图片发布后持续运行，stderr为空。抽样时CPU约0%、RSS约17MB。
- 当前四次本机健康读取约2–5ms；公网认证状态四次均200，约0.79–1.87秒。这只能证明该时段可达。
- 隧道日志在图片发布之前已有断线/TLS/DNS错误；最近一次明显故障为09-30 05:18–05:26（北京时间），之后重新连接。未据此断言网络已永久修复，也未重启健康隧道。
- 同一活跃长会话，2秒owner查找两次都失败；5秒查找两次分别在约12.9秒和2.8秒完成，另一次5秒查找本身超时。
- 对原发送前的两次只读owner/快照核验逐段测量：约6.46秒与11.51秒，每次传输约29MB，合计18.15秒。原Node子进程统一16秒终止，所以正常的大快照核验也可能未完成就被截断。原超时处理对所有写操作都返回unknown，未区分是否已经提交。
- 发送账本有两条旧unknown，其中一条仍在待发区。按请求ID检索原记录和当前已加载桌面状态，没有取得明确接收证据；没有以“没找到”反推未发送，也没有补发或删除。unknown首条会阻止自动出队，是“后续排队却没执行”的另一种可能原因。

这些证据证明了当前的超时设计缺陷；不能倒推每一次过去的失败，也不能把隧道问题全部归因于图片功能。

## 修复

1. 普通消息发送的桥接总预算调整为45秒，保留两次原owner/状态核验。历史首次仍快速回退，近期重试的owner查找预算增至10秒；完整历史读取的16秒外层上限保留。
2. 直接发送与待发项的“直接发送”约1秒内返回现有账本回执；耗时操作返回202/pending，原操作继续一次。网页仅GET同一requestId，等待接受、拒绝或未知结果，不重复POST。离开页面取消查询，不取消或重放原操作。
3. Python仅输出不含内容的preflight/dispatch阶段标记。Node终止后先等待stdio排空：确认停在preflight才可报告“尚未发送”；开始dispatch、旧协议无标记或无法确认排空都保持unknown。终止临界点的dispatch标记也有回归覆盖。
4. 原历史已确认accepted后，迟到的桥接错误不能把它降为unknown。服务重启会把所有遗留pending（包括直接发送）标为unknown，不自动重放。
5. 待发首条为unknown时，标题明确提示“等待核对首条消息，自动发送已暂停”，不再继续承诺当前轮结束就自动发送。

已有未知项保持原状。发送账本、原模型/权限、同源认证、修订校验、审批和停止边界保持。

## 验证

- HTTP回归先复现旧流程等待最终200，修复后及时返回202；同ID再次POST和后续GET不会增加实际dispatch次数。
- 受控390px浏览器把发送核验延迟到18.5秒，约1.03秒收到pending，约19.08秒自动确认；另一个待发项直接发送也只执行一次。两次实际调用、三个POST（直发/入队/直接发送）及只读轮询，无页面错误。
- 已覆盖进程超时阶段、终止竞态、旧协议降级、确认状态不回退、重启pending保护、收据ID匹配和页面离开取消查询。
- 全量150项检查通过。正式390px浏览器的受控回显只POST一次，约1.34秒202/pending、29.28秒确认accepted；原记录同一turn、唯一回复标记、0工具调用，原归档已恢复。
- 正式回读还暴露了历史延迟：AI最终回复在提交后约30.64秒落盘，网页86.42秒才显示，差约55.8秒。发送修复通过不等于读取稳定；后续需针对历史请求分段计时，不据此再发同一条消息。
- 正式版本以CURRENT.md为准。网络长期稳定性、iPhone主屏幕后台切换仍不能由这次测试推定。
