## 启动画面为什么重现

在同一 390×844 浏览器中比较修改前后的生产构建，分别延迟入口脚本、认证、App 分块和目录响应。原实现依次创建静态 HTML、认证、Suspense 和目录阶段的四个加载节点；标志位置始终为 `x=163, y=347.25, width=64, height=64`，但每次替换都让圆点动画回到零。这解释的是画面重新出现，不是标志位置移动。

现在把唯一的启动节点放在 React root 外。每个加载阶段持有同一个节点，最后一个阶段释放后在下一帧隐藏；紧接着出现的新阶段取消隐藏。释放幂等，支持重叠持有和 StrictMode，沿用原重试入口，不在切换时重启动画。

已安装的 `navigator-public-shell-v5` Service Worker 会缓存裸路径 `/startup.css`。只修改 CSS 会让旧缓存覆盖新版隐藏规则，因此生产入口按构建哈希引用 `/startup.css?v=<build>`，利用既有 Service Worker 对查询参数的放行读取匹配样式；不依赖新 Worker 激活后才生效。

## 新建直接起笔

- 普通“新建会话”在点击事件内立即开始剪贴板读取，然后处理待保存内容；Query 始终在工作目录之前并取得焦点。
- “清空”只清 Query 并恢复输入焦点，目录、归属项目和标题保留。剪贴板读不到时提示手动粘贴。
- 用户输入、清空或提交后，晚到的剪贴板结果不能覆盖当前内容。超过 16000 字显示错误且禁止提交，不静默截断剪贴板。
- Query 有内容时“创建并发送”；留空时“创建会话”，不产生首条消息。标题留空不传名称，沿用原 Codex 拟题路径。
- 恢复未完成创建时保留原 Query，不读取剪贴板；保存操作完成后重新检查最新回执，已经成功则打开原结果，避免再展示可重复提交的表单。
- 原剪贴板一键创建入口仍可用，目录记忆与提交可见性沿用前一轮实现。

## 2026-10-10：默认只起笔

按方帅要求，目录、归属项目和标题默认折叠到“更多设置”。默认只显示Query、清空，以及同一行的设置入口与创建按钮，关闭由弹窗右上角处理。有效的上次目录/项目继续复用；展开和收起不清除任何填写内容。

## 2026-10-11：新建不再触发系统Paste

这一方案同日按方帅后续选择撤回，当前行为见下一节；保留原因和验证记录供回溯。

方帅报告点击加号后，先在按钮附近出现“Paste”，选择后才看到新建窗口。原因是 `showNewConversation → prepareCreationDialog → beginCreationClipboard` 在打开表单前调用 `navigator.clipboard.readText()`；即使不等待其Promise，WebKit仍可能显示系统许可界面。[WebKit官方说明](https://webkit.org/blog/10855/async-clipboard-api/)明确描述iOS会出现只有Paste选项的callout。该控件不属于Pocket DOM，不能通过网页样式隐藏。

当前删除新建入口的自动剪贴板读取、Promise传递和预填effect，Query恢复为普通字符串状态；不新增粘贴按钮。点加号直接进入表单，需要时由用户在Query输入框中正常粘贴。清空、目录/项目记忆、可选标题及未决创建恢复保留；flush后仍重新检查原操作，已完成就打开原会话，不重新创建。附件输入框的粘贴图片事件不受影响。

624项回归及构建通过。11项完整应用浏览器检查覆盖加号与空列表新建入口，实际 `navigator.clipboard.readText` 调用计数为0；包含目录准备期间输入、清空聚焦、标题省略、折叠设置、上次目录/项目、空白创建和320px无溢出。2次创建与1次首发均在合成后端，0次真实创建/发送；证据 `.local/qa/creation-no-paste-2026-10-11/`。浏览器核对的是不再请求剪贴板，不把它表述为隐藏或绕过iOS的系统许可。

## 2026-10-11：恢复自动剪贴板预填

方帅明确：“这样的话还是保留这个机制吧，我还是需要剪贴板的。”据此恢复原点击内读取、Query预填、失败手动输入提示，以及迟到结果不覆盖输入/清空/提交的保护。iOS需要许可时仍会显示Paste；保留自动带入的便利优先于消除这一步。恢复未决创建仍只核对原请求，不读取新剪贴板。

此项恢复仅涉及原新建链路，目录记忆、默认折叠、标题可选、附件和其他已发布功能保持。628项回归及构建、17项合成浏览器检查和公网模拟剪贴板预填通过；没有读取真实剪贴板或真实创建/发送。验证证据放在 `.local/qa/creation-clipboard-restored-2026-10-11/`；最新发布身份以[CURRENT.md](../../CURRENT.md)为准。

## 2026-10-25：读取失败的恢复

欧吉安反馈新建不能自动带入剪贴板。只读核对确认，最近的重命名清空与创建提速没有修改剪贴板链路；`readText`仍在点击调用栈内发起。Chromium/WebKit的12个合成场景中，普通成功、迟到成功与输入保护正常；格得当前没有活跃创建操作，但这不能排除手机本地恢复状态或系统许可问题。

已确认的缺口是读取拒绝后只有手动粘贴说明，读取一直未返回时空输入区也没有状态/恢复入口。手机系统Paste许可是否受窗口/焦点时序影响尚未真机证明，不能把这种猜测写成根因。独立fixture并发调用两次开窗会丢掉第一次读取结果，但未证明实际App两次tap可达，本轮不据此改动开窗流程。

修正范围是保留默认自动读取和iOS必要的Paste许可，给空Query提供框内“粘贴剪贴板”动作，并通过placeholder反馈读取状态，不增加工具栏或占位提示块。主动读取继续在点击内发起，以尝试代次和输入revision保护新内容；旧自动读取、旧重试以及输入/清空/提交/离开后的迟到结果不能覆盖当前稿。恢复未决创建仍保留原内容，不读新的剪贴板。

实现保留默认自动读取；显式粘贴先聚焦原输入框，再在同一点击调用栈发起读取。读取中仅更换placeholder，空输入按钮保持可点；显式读取返回空字符串提示“剪贴板中没有文字。”，默认自动读取为空则保持安静。无法取消系统Clipboard请求时，只取消旧结果的接纳权，不声称已取消系统许可。

相关21项、两浏览器41项恢复/迟到保护与全量1360项回归通过；独立CR及构建通过。按钮44×44且未增加输入区高度，浏览器与临时服务已关闭。证据入口 `.local/qa/creation-clipboard-2026-10-25/independent/` 的 `report.md`、`probe-result.json`、`implementation.md`与`recovery-verdict.json`；未读取真实剪贴板、未创建或发送真实任务。iPhone系统许可的具体失败原因仍待实际反馈，不能将合成浏览器成功表述为真机已经恢复；最新发布状态由CURRENT维护。

本轮恢复优化已发布：源码 `8425905b58c3568e8601b171a6d95656f12d42e6`，build `034fba2005fcd1185bca4c37959ef2bacf80c2d4a2ea7a644c599ab4070d7d23`，Pages `0e230f78-ee52-45f0-adbd-3d33896aecf7`；一次上传，29个公开文件匹配和功能回读通过。两机服务、Codex与连接器未重启。用户关于手机是否出现Paste、点后仍空或提示读取失败的补充尚未返回，后续据此继续定位实际系统行为。

## 2026-10-26：Paste出现但未预填

欧吉安补充：“剪贴板有东西，点加号有paste，但是输入框没有被预填好。”这确认系统菜单会出现，不能继续只用模拟readText成功来评价问题。上一轮只修复了失败后的恢复路径，未确认这次手机未预填的根因。

本轮使用隔离iOS模拟器与合成剪贴板，记录调用返回、原生Paste、modal/focus、input事件和Promise结果顺序；Mac真实剪贴板和真实会话不作测试对象。研究与原生证据保存在 `.local/qa/creation-clipboard-2026-10-26/`。

固定WebKit源码核对表明，PR67845修改的是Promise settlement排队顺序，不能解释成Paste许可请求已改为异步。`showModal`/DOM focus也没有直接等同原生resignFirstResponder或拒绝许可的源码证据。对应源码、官方文档和反证见证据目录的`research/report.md`、`research/source/report.md`。

真实原生验证结果：

| 路径 | 结果 |
| --- | --- |
| iOS26.5 Safari，最小原生页面 | 实际HID点击系统Paste后，37字合成文本成功填入 |
| iOS26.5 Safari，当前Pocket React组件 | 系统Paste后字段43字、可编辑、无失败提示 |
| iOS27 Safari，当前Pocket React组件 | 系统Paste后字段43字、可编辑、无失败提示 |
| iOS27，实际从主屏幕打开的Web App | `displayModeStandalone`与`navigatorStandalone`均true；系统Paste后字段41字、可编辑、无失败提示，主侧另行GET回读一致 |

上述观察中，系统许可等待发生在`readText`返回之前。26.5的Promise fulfilled先于modal，27 Safari/PWA则晚于modal，但随后均正常预填；这证明了排队顺序差异，没有证明它会造成文字丢失。三次React检查没有记录到beforeinput/input/change/paste事件，未复现“focus抢走Paste”或输入事件提前取消读取。原生模拟器仍不能代替用户物理设备、第三方输入法、真实剪贴板内容类型及当前网页版本，所以本轮不据猜测修改产品或重新发布。

最小手机对照已询问：在同一个空白新建框里点右上角“粘贴”，看能否带入、是否提示读取失败或没有文字；另询问主屏幕/Safari和豆包/系统键盘环境。结果尚未返回。若手动粘贴成功，再重点对照第一次读取与预填归属；若失败或为空，继续核对系统许可/内容类型，不自动重试权限或覆盖用户输入。

原生证据在`ios/`与`react/events.jsonl`；PWA独立回读为根目录`pwa-independent-readback.json`。XCUITest无法完成系统Paste，改用已有固定`serve-sim 0.1.48`镜像与按OCR精确定位的HID实际点击；普通菜单使用原生AX。验证方法与清理要求已写入[QUALITY](../QUALITY.md#原生剪贴板验证)。

收尾已回读：三个一次性设备和其镜像helper均停删，工具无剩余session/claim，剪贴板共享设置恢复原值，原CurrentDevice未变；两个本地fixture停止，产品4397/4399服务未动。必要截图与事件保留，重复截图约1.58MB已清理。回执见`ios/cleanup.json`及`react/cleanup.json`。日志中的较长许可等待包含测试工具操作时间，不能当作产品性能数据。

用户随后反馈框内粘贴“好像有时候可以，有时候不行”，并明确“我在观察下吧”。因此保留当前版本、暂不继续改动剪贴板；尚未取得失败时具体提示、输入法和内容类型，不能把间歇性反馈归因到某个已证实原因。之后有新的实际现象再接续。
