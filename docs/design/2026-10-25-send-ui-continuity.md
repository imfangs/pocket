# 输入与发送后的画面连续性

2026-10-25。欧吉安明确此前“发送不顺滑”主要是“输入框、键盘或发送后的画面不连贯”。本轮据此修复前端交互，不把此前后端等待候选当作已确认根因。

## 已复现问题

1. 触摸发送使焦点离开textarea；长Query清空后输入区先缩到普通编辑高度，pending结束又突然收成46px。Chromium/WebKit真实页面tap均复现，原textarea节点并未重建。不同长文本样本的高度为272或348 → 168 → 46px。
2. 发送pending期间用户主动上滚，迟到accepted即使没有新正文也拉回底部。两组隔离回放分别测到scrollTop 0→3355、100→2059。源头是receive再次无条件设置nearBottom=true。

均使用合成API、唯一requestId与真实表单提交；无真实会话发送。HTTP测试源使用localhost安全上下文，初始harness的randomUUID不可用已纠正后重跑，不能归为产品缺陷。

## 修复与边界

- 只在原textarea当前聚焦、普通新发送、主鼠标键且非IME组词时，取消发送按钮mousedown的默认焦点转移。触摸产生的鼠标阶段同样适用；不取消touch pointerdown（WebKit可能丢click），不在回执后异步focus。
- 中文输入法尚在组词时保持原生焦点/提交过程；键盘Tab到按钮、核对旧发送、重试连接和取消归档不使用该保护。useReadingComposer仅暴露既有composing状态，未改键盘高度检测或IME状态机。
- 保留submit当下跟随新消息的意图；receive只更新回执和反馈，不覆盖等待期间的新阅读位置。正常贴底继续按既有规则跟随，上滚后保留位置。
- 原textarea、下一条草稿、选区、明确收起输入、附件、未知回执和同requestId防重均保持。未重写提交卡/历史消息动画，也未解除后端确认期间的发送互斥。

入口是 `Conversation.tsx` 与 `useReadingComposer.ts`。证据在 `.local/qa/send-ui-2026-10-25/`，含原触摸/回执基线、最终流程与逐帧几何。浏览器焦点、CDP触摸及注入视口检查不代表实际iPhone系统键盘动画已验证。
