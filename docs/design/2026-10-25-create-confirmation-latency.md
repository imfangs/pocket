# 新建会话的确认延迟

2026-10-28接续：[提交后回列表与行内确认](2026-10-09-creation-and-send-feedback.md#2026-10-28提交后回列表行内确认)替代下文完成后打开详情的交互；独立核对时序保持，并增加后台首消息确认与弱网列表退避重试。

2026-10-25。欧吉安反馈新建后等待很久，无法及时确认创建完成。本轮区分原生创建、首条消息持久入队和浏览器获知结果三个阶段；优先修复已复现的前端额外等待。

## 证据与判断

- 格得最近20次成功创建的账本耗时中位数3050ms，范围2714–4717ms；最新三次2714/2735/2989ms。末次原生checkpoint与首条派发登记相差约200ms，派发登记几乎与创建完成同时发生。`updated_at`与文件mtime可能包含后续恢复，不能当作逐阶段埋点；这些是当前保留账本的观察。
- 豌豆仅有三次较早记录，最近为10-20，不能用于判断10-25更新后的真实创建耗时。
- 真实LifecycleService与DesktopService的隔离探针中，即使owner history一直挂起，创建后持久入队仍在3.03ms内完成。`enqueue:true`不等待owner连接或模型执行，首条消息交接不是此次确认延迟的已证实瓶颈。
- 真实hook配合合成HTTP：后端立即就绪时，空闲轮询仍在提交后3701ms才首次核对、3810ms才显示完成；旧归档检查延迟6秒时，首次核对推迟到7349ms、完成反馈7404ms。每个场景只有一次创建POST。

原因是新建没有唤醒已经安排的4秒空闲计时器，全局读取又等待整个旧操作批次结束。原生创建约3秒与这段额外等待是不同成本。两次官方短进程、设置持久化和独立回读暂无可安全删除的已证实冗余，本轮不改后端创建语义。

## 修正范围

给正在新建的请求独立、及时的状态读取，收到带服务端createdAt的pending回执后立即核对，避免提前读取尚未登记的客户端占位请求；慢旧归档不阻挡新建确认。同一requestId的自动和手动检查共享在途GET，前台和网络恢复及时重查，后台和离开后停止当前视图读取。按本地观察时间，前10秒每次读取结束后间隔500ms，10–30秒为1500ms，随后4000ms；网络错误额外退避，恢复成功或重新联网后及时核对。

仍只提交一次POST，未知结果不自动重放。成功后沿用现有合入真实会话、后台更新目录和打开会话逻辑；用户已关闭表单或切换位置时不抢回页面。仅有threadId或客户端占位不代表已创建。

“已创建但首条消息交接未知时，表单仍写正在创建且缺少打开入口”已记录为边界体验问题，本轮不将其当作主要耗时原因，也不扩大成提前接管会话。
