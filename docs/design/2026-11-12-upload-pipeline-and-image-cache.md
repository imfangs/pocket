# 上传不中断输入与私有图片缓存

2026-11-12。欧吉安希望一次发送最多16个附件，上传不再阻挡提交，并提高网络利用率。此前提出的上传8／正文预取4／图片读取4／媒体16路，随后按用户要求翻倍。本页记录实现契约；最终源码、部署与验收状态只看 [CURRENT.md](../../CURRENT.md)。

## 并发与容量

| 通道 | 当前预算 | 归属与保持条件 |
| --- | --- | --- |
| 附件数量 | 每条16件 | 客户端、HTTP、原桌面适配器一致 |
| 附件上传 | 16路 | 浏览器上下文共享公平调度；Mac服务同时接收入流最多16路 |
| 原件 SHA-256 | 2路 | 独立于网络槽，避免同时持有16份大文件的散列缓冲 |
| 后台正文预取 | 8路、固定8候选 | 前台立即抢占；同会话共享一次读取 |
| 私有图片读取 | 8路 | 同内容单飞、惰性读取、可取消 |
| 音频／视频流 | 共用32路 | Mac服务共享流预算，取消／结束释放，原Range与背压保持 |
| 同会话原生发送 | 1路 | 保持FIFO、原requestId、指纹及修订保护 |

网络槽不是容量承诺。原件与可发文件仍最多20MiB；Mac附件总额1GiB、最多2000条。接入计入正在接收的文件、转换／预览预留和已持久的缺失附件声明，空间不足时不能靠16路并发绕过额度。普通文件、图片及各预览通道的格式／大小上限没有随路数翻倍。

共享常量来自 `shared/attachment-limits.mjs`；浏览器上传与散列分别由 `src/attachmentUploadScheduler.ts` 调度，Mac准入在 `server/attachments.mjs`。正文与媒体预算分别在 `src/prefetchPriority.ts` 和 `server/message-files.mjs`。这不是一个所有请求共同等待的全局串行锁。

## 一次提交、同一消息行

选择附件后可以立刻发送。`src/attachmentSubmissionManager.ts` 将已捕获的File、uploadId、文字和requestId从输入草稿转给独立提交所有者，消息列表立即保留一行「上传中」。输入框可以继续写下一条；切换详情不把原文件放回新草稿，也不重建上传编号。已经开始的PUT继续用原身份完成，不为绑定消息再传一次。附件正在移除或删除结果待核对时，拒绝草稿归属转移。

`POST /api/tasks/:id/messages` 新增互斥的 `attachmentUploads` 清单，与旧 `attachments: string[]` 完成态接口兼容。清单包含id/name/size/mime和可选sourceSha256。Mac以原requestId持久保存不可变提交意图与清单，新增 `attachment_upload_messages`、`attachment_upload_claims`，先保留队列位置；未完成的附件不是可派发快照。后续PUT可以带requestId，普通上传与内部反馈上传仍使用各自归属。

全部原件到齐后，再逐件核对原件字节／SHA、转换件、记录和归属，在事务中绑定规范附件与原派发指纹，转为ready。之前不访问原owner历史、不打开会话、不发部分附件。ready只证明文件齐了；只有原发送回执accepted使该消息行变绿，少附件或只有同文字的历史回显不能代替回执。上传状态与派发状态分开，原自动直发偏好、暂停、FIFO和队列修订继续有效。

未知上传回复先GET原uploadId；未知提交回复只GET原requestId，不自动重复PUT或POST。确定失败的附件可显式重试原文件／原ID。取消先核对原发送状态和队列revision，再撤销远端消息与附件；迟到accepted优先，已经发送不能被本地取消覆盖。清理回复丢失仍保留继续核对／重试取消入口，不提前删除恢复信息。

浏览器File留在页面进程内，Mac持久的是提交意图、已到达文件和缺失清单。iOS挂起或杀死PWA后不能承诺继续上传；恢复后的缺失文件需要重新选择或取消后重提，服务不会因页面消失而发送部分内容。公开壳和阅读缓存不持久化File、发送权限或未知回执。

## 图片缓存与访问证明

复用已有 `idb`，新增浏览器私有 `pocket-image-read-cache-v1`，与文字ReadingCache分开：L1最多12MiB／256项，整个IndexedDB图片库最多64MiB／256项，按近期访问淘汰。图片缓存上限独立于最多缓存会话设置和正文30MiB预算；超出额度或持久存储不可用时，保留当次可读结果并退回内存。

本轮实际WebKit浏览器验证发现，图片能够解码，但将Blob直接put进IndexedDB会报UnknownError。持久记录改存ArrayBuffer字节和原MIME／大小／SHA等元数据，读取还原Blob；已有Blob记录仍兼容，读取时迁为字节表示。异步转换前后重新核对撤销代次，不让转换延迟越过退出／清理。该兼容需要实际浏览器回归验证，不能由Node的fake-indexeddb通过替代，也不据此宣称所有实体iPhone存储行为已实测。

只接受服务登记的 `images/:key`、`files/:key/image` 和 `attachments/:id` 原件／预览路由，不从任意路径或外站URL生成读取能力。缓存key使用machine、fresh source scope、threadId、内容SHA与original／preview变体。认证检查只恢复会话级使用条件；磁盘复用还需要当前来源scope及有效登记，不从旧缓存目录取得新授权。没有SHA的已登记图片仅用本次会话L1／单飞，不能写入磁盘。

网络和磁盘结果都核对机器响应、大小、真实图片签名、MIME及已知SHA；命中L1或同一个在途读取的消费者仍核对各自MIME／size。失败、权限拒绝、错机、哈希错误或超限响应不写成缓存内容。图片请求保持同源认证、客户端版本及no-store，不加入Service Worker或公开构建。

一般图片／图片文件子路由与缩略预览最多8MiB；附件原图仍支持20MiB。超过8MiB的附件原图不落IndexedDB，可以保留当前查看层的短期Blob租约。上传图片公开元数据增加previewSha256／previewMime／previewSize，缩略图和原件分别核对，不能拿原图SHA证明另一份缩略图。

消息图、附件缩略图和大图查看器共享读取：同内容单飞，每个消费者独立取消；最后一个消费者退出才停止底层读取。Blob URL按租约释放，L1淘汰不使仍打开的图片突然消失。主动重试强制读原路由，旧查看层租约仍可正常关闭。

退出、401、切来源、清缓存和跨标签失效撤销相关内存、在途请求、URL租约及磁盘可读代次，迟到写入不能把旧内容复活。冷启动取得相同新鲜scope时保留已验证磁盘记录；来源变化仅清所选机器的其他scope。缓存不能修复第一次访问时的Mac目录权限拒绝，仍按 [图片权限](../IMAGES.md#mac-文件访问权限) 调查。

原浏览器已解码的图片在同页重复打开可能本来就不再请求。新缓存的增量是已验证内容的冷重开／离线复用和跨组件单飞，不能把旧同页行为宣称为从三次传输变成一次。

## 正文预取与展示边界

8个候选仍先由原rank／有效未读／运行状态确定，再检查缓存，不能跳过命中后不断补足到8路而下载整个目录。慢槽不阻止其他空闲槽调度到期读取。前台读同ID接管已有flight，其他后台读取让位；一次批量取消只增加一次全队列冷却。弱网退避、离线／不可见暂停保持，正文预取不自动连接owner、不标读或核销发送回执。

同scope的已验证版本地板独立保留最多256项标量元数据；会话离开rank工作集、临时成为当前详情或正文被淘汰时，不接受3→2回退。scope失效／stop清理地板，第257项按LRU淘汰；较高版本仍可进入。运行约5秒／未读约30秒是可调度间隔，不是网络完成时限，也不保证第9个未读立即命中。

已上传图片的保存历史包装另见 [用户附件展示证明](2026-11-12-uploaded-user-envelope.md)。完整真实typed图片结构与精确已知包装可产生attachmentEnvelope显示证明，前端据此抽取实际Query；图片读取URL还必须精确匹配同线程已存在上传记录。typed图片没有对应记录时仅显示无链接、无图片请求的「附件需在 Mac 中查看」卡。新包装的raw text、id、role、turn与指纹保持；显示证明不核销回执，分页 `transcript-page` 同样富化。纯文本伪造、引用、代码、未知或截断包装保留原文，不能由解析器授予文件或发送能力。
