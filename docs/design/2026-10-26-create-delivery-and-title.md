# 新建首条消息与标题同步

2026-10-26。用户通过真实使用反馈表示：“好像如果我不点直接发送，这个会话就不会继续，状态通不过来，标题也没有自动同步过来”。本轮核对反馈、同一次访问的回放、Pocket 请求账本与原生历史，修复两个可以独立复现的等待点。

## 观察与原因

回放中，创建确认后首条消息仍在待发区；连接提示消失后仍有一段等待，用户点击“直接发送”后看到“已发送”。原生记录从首 Query 登记到开始运行约19秒。手机与Mac时钟没有校准，不能凭亚秒时间先后断言手动和自动派发谁先抵达，也不能把全部连接耗时都归因于队列。

已确认的实现缺口：新建首 Query 先安全持久入队，后台按会话串行检查；旧会话的慢读取会阻止后面的新会话开始检查。连接成功只更新历史缓存，没有唤醒该会话队列；手动直接发送能绕过全局等待。真实账本中存在旧队列，合成场景已复现相同等待形状。

标题是独立问题：原生自动命名写在SQLite的 `name`，旧 `title` 保留首Query属正常结构，Pocket来源已经正确优先读取 `name`。但界面只随45秒目录周期更新，正文或运行状态的新结果不刷新标题。回放确认打开信息时仍是首Query，原生此时已生成名称。没有复现“不发送就停止所有状态轮询”。

## 当前行为

- 明确提交或连接使原owner确认 `resumed` 后，运行中的Pocket后台立即检查该会话队列，使用刚取得的状态；无需等旧会话检查轮次走完。
- 同会话检查保持单飞。旧读取进行中又收到连接就绪，只合并一次后续检查，避免丢掉新状态或重复派发。
- 每轮后台扫描、轮询timer与在途自动派发保留同一代次；服务停止后，迟到读取和附件准备不再开启自动发送，重新启动也不复活旧循环。
- 仍检查原队首、原 `autoDirect`、FIFO、暂停、编辑、unknown、原owner及原生发送前核验。没有升级旧队列策略，也没有增加无界跨会话并发。后台普通串行长尾与连接本身的慢读取仍分别保留。
- 当前打开的会话在原生创建后60秒内，每5秒补一次目录同步，正常最多11次；请求复用已有合并逻辑。隐藏、离线、离开或超窗后停止，重新打开及渲染不延长截止时间。原45秒周期继续负责常态同步。
